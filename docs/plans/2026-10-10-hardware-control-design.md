# SPIDER 실기기 제어 준비 설계

## 목표

프로펠러를 제거하고 FC를 디스아밍한 상태에서 XIAO ESP32S3의 AprilTag 판단이
UART5 MSP를 거쳐 FC의 롤·피치 수신 채널에 반영되는지 확인한다. 운용자는 기존
SPIDER 웹 UI에서 FC와 보드 상태를 함께 보고, 조종기 스위치로 즉시 수동 조종권을
회수하며, 필요할 때 킬 명령을 보낼 수 있어야 한다.

이번 단계는 실제 이륙이 아니라 제어 경로의 지상 검증이다. 원격 아밍, 스로틀
오버라이드, 모터 시험, 원시 MSP 쓰기는 구현하지 않는다.

## 확인된 구성

- FC: MicoAir H743 V2, INAV 9.1.0, USB `COM9`
- XIAO ESP32S3 Sense: BLE `TagBoard-B8B4`, NUS, 실행 빌드 `TAGVISION-20261010-20`
- XIAO ↔ FC: UART5 MSP 115200, 응답률 99.9% 이상
- MTF-01P: FC UART4 MSP에 직접 연결. FC에서 거리센서·광류가 정상 감지됨
- 수신기: UART6 iBUS
- 비행모드: ch5 ARM, ch6 MSP RC OVERRIDE, ch7 FAILSAFE, ch8 ANGLE
- 현재 오버라이드 마스크: `64`(ch7 킬만)
- 첫 채널 시험 마스크: `67`(롤+피치+ch7 킬)
- 스로틀과 요, ARM 채널은 ESP32가 덮어쓰지 않음

## 접근

기존 브라우저 Web Bluetooth와 로컬 FastAPI 백엔드를 결합한다.

- 브라우저는 사용자 제스처가 필요한 BLE 연결을 소유한다.
- XIAO 상태 JSON을 브라우저에서 파싱하고 허용된 보드 명령만 NUS RX로 보낸다.
- FastAPI는 COM9를 짧게 열어 FC 상태와 설정을 조회한다.
- FC 설정 쓰기는 `msp_override_channels`의 RAM 변경만 별도 안전 모듈에서 허용한다.
- UI는 보드 텔레메트리와 FC 조회 결과를 합쳐 단일 준비 상태를 표시한다.

백엔드가 BLE까지 소유하는 구조는 Windows BLE 연결 독점과 이벤트 루프 복잡도가
커서 첫 시험에 불필요하므로 사용하지 않는다.

## 데이터 흐름

1. UI가 BLE로 `TagBoard-B8B4`에 연결하고 `info`를 요청한다.
2. 보드는 `info`, `msp`, `fc`, `vision`, `flow`, `mic` JSON 줄을 알림으로 보낸다.
3. UI가 `/api/hardware/fc/status`를 호출해 COM9의 식별, 무장 상태, RC, 모터,
   센서, 모드 범위, `msp_override_channels`를 읽는다.
4. 순수 판정기가 두 입력을 합쳐 각 안전 게이트를 통과/차단으로 분류한다.
5. 모든 RAM 적용 조건이 맞으면 UI가 일회성 확인 절차를 거쳐 마스크 67 적용을
   요청한다.
6. 태그를 움직이면 보드의 `msp.out`과 FC의 `MSP_RC` 롤·피치가 함께 변한다.
7. ch6을 2000으로 올리거나 `msp off`를 보내면 보드 제어를 회수한다.
8. 시험 종료 시 마스크 64를 RAM에 복구한다. 전원을 껐다 켜도 영구값 64로 복귀한다.

## 안전 게이트

### RAM 마스크 67 적용 조건

- 하드웨어 쓰기 기능이 명시적으로 활성화됨
- FC 식별자가 `MICOAIR743V2`, 펌웨어가 INAV 9.1.0
- FC 디스아밍
- 모터 M1~M4가 모두 1000µs
- RC 스로틀이 `min_check`보다 낮음
- 수신기 링크 정상
- UART5 MSP와 MSP RC OVERRIDE 모드가 설정됨
- 현재 마스크가 64 또는 67
- 사용자가 `프로펠러 제거 / 디스아밍` 확인 문구를 입력
- 일회성 토큰이 유효함

현재 실기기 스로틀은 약 1960µs이므로 조종기 스로틀을 내리기 전에는 적용이
차단된다.

### 비행 출력 잠금 조건

다음 항목 중 하나라도 남아 있으면 UI는 “지상 채널 시험만 가능”으로 표시한다.

- ESC가 DShot 신호와 시작 멜로디에 응답하지 않음
- 카메라/기체 축이 `axes_verified:false`
- 보드가 `-20`이며 FC 높이를 읽는 `-21`이 미업로드
- 카메라 팬·틸트가 미장착인데 소스 설정은 활성
- 실제 모터 방향·순서·공회전·킬 재시험 미완료
- Failsafe가 DROP

### 보드 명령 허용목록

- 조회: `info`, `tags`, `snap`
- 제어 경로: `msp on`, `msp off`, `mission reset`
- 비상정지: `kill`, `kill off`

`motortest`, `fcmsp`, `voicecmd`, 임의 문자열, 아밍과 스로틀 명령은 UI에서
보내지 않는다. `kill`은 즉시 실행하고, `kill off`는 확인 후 실행한다.

## 판정 오류 수정

현재 로컬 FC 도구에는 두 가지 오진이 있다.

1. INAV 9.1의 permanent mode ID 50을 `LOITER CHANGE`로 표시해 실제
   MSP RC OVERRIDE 스위치를 “없음”으로 판정한다.
2. MTF-01P가 MSP 장치로 UART4에 연결된 구성을 전용 `OPTICAL_FLOW`와
   `RANGEFINDER` 직렬 기능이 없다는 이유로 실패 처리한다.

모드 ID 표를 실기기 `BOXIDS`와 저장소 문서에 맞추고, 센서 하드웨어가 MSP이며
FC가 레인지파인더·광류를 감지하고 UART4가 MSP인 경우를 정상으로 판정한다.

## UI

기존 하단 XIAO 영역을 “실기기 제어” 패널로 확장한다.

- 연결: BLE, FC USB, XIAO↔FC 링크
- FC: 무장, 차단 사유, 스로틀, 모터 4개, 전압·전류
- 센서: 카메라, 태그, MTF 거리·광류, 수신기
- 제어권: ch6 상태, 마스크 64/67, 보드 송신값과 FC 적용값
- 안전 게이트: 통과/차단 목록과 정확한 다음 행동
- 명령: 상태 요청, MSP 시작/중지, 미션 초기화, 킬/해제
- 시험: RAM 67 적용, 64 복구, 채널 반영 비교

위험 동작은 색뿐 아니라 텍스트, 아이콘, 확인 문구로 구분한다. BLE 연결 해제,
FC 타임아웃, 보드 `fc_link:false`, 아밍 감지는 즉시 제어 패널을 잠근다.

## 오류 처리

- COM9 사용 중이면 쓰기 없이 “포트 사용 중”을 표시한다.
- BLE가 끊기면 마지막 값을 stale로 표시하고 모든 일반 명령을 비활성화한다.
- FC 되읽기 값이 요청값과 다르면 EEPROM 쓰기 없이 중단한다.
- RAM 변경 뒤 상태 재조회에 실패하면 사용자에게 전원 재인가로 64 복구를 안내한다.
- 브라우저 새로고침 시 위험 확인과 토큰은 폐기한다.

## 시험 전략

1. 모드 ID 50과 MSP 센서 구성에 대한 회귀 테스트를 먼저 실패시킨다.
2. 안전 게이트 순수 함수의 허용·차단 경우를 테스트한다.
3. 가짜 FC로 64→67→64 RAM 변경, 무장·스로틀·모터 차단, 되읽기 불일치를 테스트한다.
4. API에서 쓰기 비활성, 잘못된 확인 문구, 만료 토큰, 포트 오류를 테스트한다.
5. 프론트엔드 빌드로 TypeScript와 UI 통합을 검증한다.
6. 실기기에서 읽기 전용 상태를 먼저 확인한 뒤, 조건 충족 시 RAM 변경과 채널
   반영만 시험한다. 아밍과 모터 출력은 하지 않는다.

## 첫 완료 기준

- FC/보드 정보가 한 화면에서 일치한다.
- MTF-01P와 MSP RC OVERRIDE가 오진 없이 정상으로 표시된다.
- 안전 조건이 맞지 않으면 RAM 쓰기가 거부된다.
- 조건 충족 시 마스크 67이 RAM에 적용되고 되읽기된다.
- 태그 이동에 따라 보드 롤·피치와 FC 적용 롤·피치가 같은 방향으로 변한다.
- ch6 수동 전환 또는 `msp off`로 중립/조종기 입력으로 복귀한다.
- 시험 후 마스크 64가 복구되고 모터 출력은 전 과정 1000µs다.
